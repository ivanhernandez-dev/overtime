# 0027. Background commands and claude -p runs keep the Mac awake while they run

- **Status:** Accepted
- **Accepted:** 2026-10-22. The project author chose an automatic detection for the release after 1.1.0: on by default, as an explicit exception to the rule that a default reproduces how the previous release behaves; no time limit by default, with an optional limit of 2 hours; every Claude Code session, terminal or not; and a waiting state in the panel's session rows. The author also decided that a live `claude -p` process counts as Claude working for as long as it lives, whatever started it. The signal (the two markers and the 30 s age), the one shared limit, the copy, the row precedence and leaving Agent SDK scripts out were delegated to Claude; the author may revisit them.
- **Date:** 2026-10-22
- **Deciders:** Project author
- **Related requirements:** **DET-13**, **DET-14**, **DET-15**, **DET-10**, **DET-03**, **DET-04**, **DET-12**, **APP-01**, **APP-13**, **OPS-03**, **OPS-05**
- **Related ADRs:** [0017](0017-ignored-entrypoints-sdk-prefix.md), [0019](0019-detection-loop-energy-design.md), [0023](0023-the-panel-lists-the-claude-sessions-that-are-working.md), [0024](0024-configurable-battery-and-temperature-protection.md), [0025](0025-lid-closed-keep-awake-setting-and-custom-durations.md), [0026](0026-keep-awake-automation-url-scheme.md)

## Context

- **Claude waits on commands it started.** Claude Code can run a command in the background: the turn ends, its status line shows the running shell, and Claude carries on when the command finishes, through a task notification. Claude Code drops its own `caffeinate` about 30 s after the turn ends, while the command still runs. Overtime let go about three minutes after Claude's last activity, so with the lid closed the Mac slept, the command paused and Claude stalled until someone opened the lid. One session was seen waiting 21 minutes on a background script with no `caffeinate` the whole time.
- **`claude -p` runs never counted.** Review tools, scripts and scheduled jobs that run `claude -p` (the non-interactive mode) were never seen as Claude working: `claude -p` starts no `caffeinate`, even while it works, and its transcripts carry an `sdk-*` entrypoint, which DET-03 ignores by design (ADR [0017](0017-ignored-entrypoints-sdk-prefix.md)).
- **DET-10 as it stood:** "Background tasks (for example dev servers) and `/loop` wakeups do not keep the Mac awake. This is intentional."
- **What Claude Code 2.1.308 does** (read from its installed bundle, behaviour only, and from an 8-minute log of the process table). Each command of its Bash tool, foreground or background, is a direct child of the `claude` process: `bash` or `zsh` started with `-c` and detached, so it leads its own process group and session and has no controlling terminal. Its command argument sources a shell snapshot under `<config folder>/shell-snapshots/` (without a snapshot, the shell runs as a login shell and sources nothing), and it always ends by writing the working folder back with `pwd -P >| <file>`. The Bash tool runs only `bash` or `zsh`. Hooks are terminal-less children too, but they run through `/bin/sh` or the user's shell without either marker, and they can run for any length (a `timeout`, or in the background with `async`). MCP servers are children in the `claude` process's own group, with its terminal. A subagent's commands are children of the main `claude` process. When Claude Code exits, it leaves its background commands running, and the kernel hands them to launchd.

## Decision

- **The background-command rule (DET-13).** A Claude Code session is waiting on a command in a tick when one of its direct children: is `bash` or `zsh` by its kernel name; has no controlling terminal; leads its own process group; is not a zombie; carries Claude Code's tool-command scaffolding in its command argument (next point); has a parent other than launchd; and has been running for at least 30 s. Its parent must be in the same sample, belong to the same user, not be a zombie, and be recognised as Claude Code by its arguments or its executable path, never by its kernel name alone. The session is that parent. Foreground and background commands match alike: a foreground command older than 30 s runs inside a turn that already holds, so counting it changes nothing.
- **The markers are required, either one.** The argument after `-c` (or after `-c -l`) must contain `/shell-snapshots/snapshot-` (the snapshot it sources) or `pwd -P >| ` (the working-folder write-back every command ends with, with or without a snapshot or the sandbox). Without a marker, a long or `async` hook, or another app's detached shell, would count, and with no default limit a false positive would hold for as long as its process lives; no minimum age can tell a long hook from a command. Two markers, because each is an internal detail of Claude Code that may change: a future version that drops both is no longer detected, which fails safe (the behaviour of 1.1.0).
- **The 30 s age.** Hooks start every few seconds in every session (775 in the 8-minute log, 732 of them gone within one 1 s sample, none older than 3 s), so reading arguments only for shells 30 s old keeps those reads at zero. And 30 s is how long Claude Code keeps its `caffeinate` after a turn: a command started during the turn is old enough by the time the `caffeinate` goes, so a terminal session's hold has no gap between the two signals. The same constant gates the scanner's read and the detector's rule.
- **Every Claude Code session (author decision).** Terminal, editor, desktop app, headless and background sessions, and a `claude -p` run's own commands, of the current user only. A subagent's commands count for its main session. A command of another user, or one whose parent belongs to another user, never counts.
- **The `claude -p` rule (DET-14).** A process recognised as Claude Code, not a zombie, with a known start, with `-p`, `--print` or `--print=…` as one of its own arguments before the first `--` (the test Claude Code itself applies, without its check that standard output is not a terminal), is a `claude -p` run. Its parent does not matter: a terminal, a terminal since closed, launchd, another Claude session's command or a script all count. It counts until the tick after the process exits; several runs hold until the last one exits. A short-flag cluster such as `-pc`, or `-p` inside another argument's value, does not count.
- **What is not counted on purpose.** A `claude` process launched with `--output-format stream-json --input-format stream-json` and no `-p`, which is how the Python Agent SDK, the desktop app's sessions and very likely the editor extension start Claude Code; `--chrome-native-host`, `--sdk-url` workers and `--init-only`; and terminal-less Claude processes in general. Those include long-lived interactive hosts that stay open while Claude is idle, so a rule on the stream-json flags, on a missing terminal or on an `sdk-*` launch environment would keep the Mac awake for as long as an editor, the desktop app or an Agent SDK client is merely open. **Agent SDK scripts are therefore not counted:** the Python Agent SDK never passes `-p`, and a Python program that keeps an SDK client open while idle would otherwise hold the Mac awake. Such a script can open `overtime://keep-awake` (ADR [0026](0026-keep-awake-automation-url-scheme.md)). Tools that run `claude -p` are counted, whatever wraps them.
- **Defaults.** `backgroundCommandsKeepAwake` true, `printRunsKeepAwake` true, `longRunningLimitEnabled` false, `longRunningLimitMinutes` 120 (OPS-05). A settings file without the keys decodes to these, which is the author's exception to the rule that defaults reproduce the previous release. A wrong type makes the file invalid like any other key; minutes outside 15 to 720 are clamped on load and recorded as an adjustment.
- **Two switches and one shared limit (DET-15).** Two switches, because the two signals fail differently: a dev server is the risk of background commands, a hung or endless loop the risk of `claude -p`, and a user who runs nightly reviews may want one without the other. One limit, because it is one idea, how long Overtime keeps the Mac awake for work Claude is not visibly doing, with one default (2 hours when turned on), one row and one sentence. Its anchors differ because the signals do. A background command stops counting that long after the latest of Overtime's last eligible transcript write, the last tick that counted a Claude `caffeinate` and the first tick that saw a command; this is measured across sessions, because transcripts cannot be attributed to sessions (ADR [0023](0023-the-panel-lists-the-claude-sessions-that-are-working.md)). New activity, such as the turn a task notification starts, moves the anchor, so the limit starts again. A `claude -p` run stops counting that long after its own start, since a run has no other activity Overtime can see.
- **Energy (APP-13).** The scan still reads the BSD info record once per pid and adds no other call per pid. Two new candidate rules read only fields of that record: an aged tool-shell shape (`bash` or `zsh`, no terminal, its own process group, not a zombie, a parent other than launchd, 30 s of age), which makes the shell and its parent candidates; and a terminal-less process whose kernel name is `claude` or a version number, as the native install's is. A candidate's arguments and path are read once per process identity (pid, start time and kernel name) and then served from the cache. See the note of 2026-10-22 in ADR [0019](0019-detection-loop-energy-design.md).
- **Privacy.** The parser reads two yes-or-no facts from the argument buffer it already reads and keeps neither the command argument nor any argument after the first. No command text is stored, logged, exported or shown: the log carries a source and a number of minutes, the diagnostics export booleans and times, and the panel shows the folder and the state.
- **The panel (APP-01).** One row per Claude Code process, so a `claude -p` run started by another session's background command and that session are two rows; holding stays a single yes or no. The precedence is: "Working · " and its time (Claude Code's own `caffeinate`, ADR [0023](0023-the-panel-lists-the-claude-sessions-that-are-working.md)), then "Working · claude -p · ", then "Waiting · background command · " for a terminal session or "Running a command · " for a session outside a terminal, which cannot tell a background command from a long foreground one. The title is the folder, from the working directory the scan reads once per listed process. A waiting row is listed only while background commands hold, and a `claude -p` row only while `claude -p` runs hold, both under ADR 0023's busy gate, so the list never shows work that no longer keeps the Mac awake. The quiet idle line counts terminal sessions only. The reason line counts waiting rows apart: "Claude is waiting on a background command.", "Claude is waiting on background commands in 2 sessions." and "Claude is working in 1 session and waiting in 1 more."; a "Running a command" row counts as working.
- **Stable durations.** A waiting row's time runs from the first tick that saw the session waiting, kept through a 6 s grace (three ticks), so a late tick does not restart it; a `claude -p` row's time runs from the run's start, frozen at the first sample. Both change only at edges, so the published snapshot stays edge-only.
- **The decision log (OPS-03).** `BUSY on source=background` and `BUSY on source=print` when busy turns on from those sources (a `claude -p` run is checked first); `BUSY continues source=background` or `source=print` when busy stays on but its reason becomes one of them, for example when a turn ends and a command keeps holding; `BUSY limit source=background minutes=120` (or `source=print`) once per episode when the limit stops a present signal; and `BUSY off source=print` or `source=background` when busy turns off while such a signal is present. A change between transcript and `caffeinate` still logs nothing, as before.
- **Placement.** A Long-running work section in Settings > Detection, after Timing: "Keep awake while Claude waits on a background command", "Keep awake while claude -p runs", "Stop after a time limit" and a "Time limit" row in minutes, dimmed while the limit is off. The ignored-entrypoints caption says that a `claude -p` run still keeps the Mac awake while it runs.
- **Detection health (DET-12).** A `claude -p` run with a terminal no longer counts as a terminal session for the "terminal Claude silent" warning: a run that persists no transcript would otherwise raise it after 10 minutes while the panel shows it working.
- **A change applies within one tick.** Applying settings publishes the new switches and limit at once and names the new keys in `SETTINGS applied`; the next 2 s tick evaluates busy with them.

## Consequences

- **A dev server Claude started keeps the Mac awake.** A dev server, a file watcher or any other command Claude Code starts keeps the Mac awake for as long as it runs and its Claude session is open, with the lid closed too, because Claude may be waiting for it. To avoid that, stop the command when you are done, turn off "Keep awake while Claude waits on a background command" in Settings > Detection, or turn on a time limit there. The panel shows the session as "Waiting · background command" (or "Running a command" outside a terminal), and the decision log has a `BUSY continues source=background` line when the turn ends and the command keeps holding. A `claude -p` run that never ends keeps the Mac awake the same way, until it exits.
- **What still lets go.** The battery limit, temperature protection, Pause, Sleep Now, "Keep awake with the lid closed", the watchdog, the 5 s system-call timeouts and the helper's own limits all work as in 1.1.0. Release Until Idle lets go at once and holds again only after Claude has gone idle and started working again, so with a dev server running it stays released until the server ends.
- **A Claude Code that exits stops counting at once.** Claude Code 2.1.308 leaves its background commands running when it exits; the kernel hands them to launchd, and a command whose parent is launchd never counts, so the next tick no longer holds and the release grace runs as usual.
- **A hung Claude Code with a live command keeps holding** until the command ends. This is the accepted cost of no default limit.
- **What stays out, failing safe.** `/loop` wake-ups between runs (DET-10), Agent SDK scripts, a `claude -p` run with no terminal started through the npm package's `node` launcher (its kernel name is `node`, too common to read for every process), and any future Claude Code version that drops both markers. Each behaves as in 1.1.0: Overtime lets go about three minutes after the last activity it sees.
- **Without background commands and `claude -p` runs, nothing changes.** Every new branch, log line and deadline needs one of the two signals, so every decision, effect and state is 1.1.0's, which the frozen suites prove.
- **Energy.** No new system call per tick for unrelated processes, no new process and no timer.
- **Privacy.** No command text anywhere. The working folder of an editor or desktop session waiting on a command is now shown and exported, as terminal sessions' already were, with the home folder as `~`.

## Alternatives considered

- **A minimum age without a marker.** Long and `async` hooks and other apps' detached shells would count, and with no default limit they would hold for as long as they live.
- **The marker as a preference.** The same false positives whenever the marker is missing.
- **`CLAUDECODE=1` in the shell's environment.** Hooks inherit it too.
- **A limit by default.** Rejected by the author: a long build or test run should not lose the hold halfway.
- **A limit per session.** Transcripts cannot be attributed to sessions (ADR [0023](0023-the-panel-lists-the-claude-sessions-that-are-working.md)), and a session outside a terminal has no `caffeinate` Overtime counts.
- **Separate limits for the two signals.** One more number for one idea; only Settings, the editor and the pane would change if the author wants it.
- **Counting every terminal-less Claude process, the stream-json flags or an `sdk-*` launch environment as non-interactive.** Editor and desktop hosts and open Agent SDK clients live while idle.
- **A candidate rule on the executable path.** The path is the expensive read made only for candidates; a rule on it would be a system call per pid per tick.
- **Reading the arguments of every shell.** Hooks start several times a second across sessions.

## Not verified

- No signed build was run on real hardware: a background command with the lid closed, a dev server overnight, a `claude -p` run started by launchd, and the Detection pane and the new rows with VoiceOver.
- Claude Code versions other than 2.1.308.
- The editor extension's launch shape: it was not installed here.
- macOS 14 and 15.
- The energy over a week (APP-13).

## Evidence

- **The process table, logged on 2026-10-22** on macOS 27.0 with Claude Code 2.1.30x: one snapshot per change of every `claude` process's shells, `caffeinate` and tool-shell children, sampled every second for 8 minutes. A turn ended and its `caffeinate` was gone about 30 s later while the session's background commands ran on for minutes; another session held a background command for the whole window with no `caffeinate` in any sample. Of 775 hook processes, 732 lived less than one sample, 11 lived 1 s, 25 lived 2 s and 7 lived 3 s. MCP servers shared their parent's process group and terminal. A headless `claude` that ran commands sat inside another session's background command.
- **Read-only reads, behaviour only** (no code is quoted here): Claude Code 2.1.308's installed bundle (how the Bash tool spawns its shells and builds their commands, which shells it accepts, the hook schema, and its own test for non-interactive mode), the desktop app's archive and the Python Agent SDK's published transport source (both launch Claude Code with the stream-json flags and no `-p`), and the live process table, read for shapes only (process group, terminal, kernel name, flag names).
- **The test suites:** `LongRunningWorkTests` (the parser's flags, the background-command rule against the logged shapes: tool shells, hooks, MCP servers, the snapshot shell, orphans, zombies, other users, non-shell children; the `claude -p` rule and the stream-json hosts it excludes), `LongRunningBusyTests` (the switches, the shared limit and its anchors, the log lines, the deadlines, and `withoutLongRunningSignalsTheDefaultBehavesAsBefore`), the new `ProcessScannerTests` (the two candidate rules, reads once per identity, `argvIsReadOnlyForCandidatePids`), `SessionReaderTests`, `EngineLongRunningTests` (the logged process shapes through the real scanner, the composition and the reducer to `BUSY on source=background`), `PanelContentTests`, `StatusPresentationTests`, `LongRunningCopyTests`, `DiagnosticsManifestTests` (`theExportHoldsNoCommandText`), `SettingsTests`, `SettingsEditorTests` and the hosted `DetectionPaneTests` and `PanelModelTests`.
- **The default without the new signals equals 1.1.0:** the frozen scenario, busy, grace, release, lid, helper and notification suites passed byte-unchanged at every commit, and the seven README images rendered byte-identical to a render of the 1.1.0 commit on the same Mac. Six also match the committed files; the setup guide's welcome image differs from its committed file in 318 pixels of the app icon, by one level, on macOS 27.0.1 with Xcode 27.1, and the 1.1.0 commit renders it the same way.
